# Hourly Impeccable refresh without incremental charges

An hourly deterministic GitHub Actions workflow is the smallest supported route for this public fork. Under GitHub's current documented billing model, each check and a qualifying routine publication can incur **$0 incremental monetary charge** when they use standard GitHub-hosted Linux execution and ordinary Release assets, with the exclusions below. This establishes the cost condition for hourly checks. It does **not** establish delivery within one hour: GitHub's scheduler is best effort, and consumer synchronization adds separate delays.

I inspected primary documentation and read-only GitHub APIs on **2026-11-06**. Repository observations were collected at **16:05–16:09 UTC**. This is a research recommendation for [Establish reliable hourly refresh within the zero-cost constraint](https://github.com/nisavid/impeccable/issues/5), not an implemented or qualified updater. I ran no workflow, build, installation, publication, billing experiment, or account mutation.

## Cost boundary

GitHub explicitly makes standard hosted runners in public repositories free independently of the account's included compute allowance. Larger runners are billed even for public repositories. Logs and job summaries do not consume artifact storage allowance. Therefore a standard Ubuntu runner with deterministic scripts needs no paid compute or model invocation for this job. An hourly schedule requests 24 checks per day, or 720 in a 30-day month; those counts do not change the public-runner exemption. No duration or actual bill was measured. [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

Keep archives as ordinary GitHub Release assets. GitHub allows up to 1,000 assets per release, each **under 2 GiB**, and states no total release-size or download-bandwidth limit. The inspected upstream `universal.zip` is 18,116,588 bytes. Release assets are the proposed distribution store; Actions artifacts, Actions caches, Git LFS, Packages, larger/custom runners, external storage, model/provider calls, and paid services remain excluded. The cost conclusion applies to that route, not to every inherited workflow or consumer subscription. [Release storage and bandwidth](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas), [inspected upstream release](https://api.github.com/repos/pbakaus/impeccable/releases/424884908)

## Smallest mechanism

Use one repository workflow on the default branch, with an hourly cron offset from the start of the hour, for example `17 * * * *` in UTC, plus `workflow_dispatch`. Use the same reviewed deterministic procedure for scheduled and manual execution. Check first; package only a new eligible input. Keep verification, Release publication, and marketplace-ref promotion in the same workflow rather than depending on a second workflow triggered by the publisher's push or release event. These are implementation recommendations, not observed behavior. GitHub supplies the schedule, manual trigger, runner, token, and Release store; the investigation found no need to add another service or a fork-sync framework. [Schedule semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [manual execution](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), [token-trigger behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs)

The existing upstream packaging work can inform the later packaging decision, but neither that source nor the platform documentation qualifies a new fork updater. Keep its procedure revision pinned and reviewed. A required procedure change stops routine promotion for review, as the approved publication policy requires.

### Select the skill stream explicitly

The repository-wide `/releases/latest` endpoint is unsuitable: at inspection it returned **`cli-v4.8.0`**, not the skill release. GitHub documents that endpoint in terms of non-draft, non-prerelease releases and `created_at`, not a component-specific semantic-version selection. List releases instead; the API supports pagination with up to 100 results per page. The inspection returned 93 records in one page, which is an observation rather than a permanent bound. [Observed generic latest](https://api.github.com/repos/pbakaus/impeccable/releases/latest), [Release API](https://docs.github.com/en/rest/releases/releases)

I recommend the following selector contract:

1. Complete the release enumeration, following pagination. Accept published records with `draft == false`, `prerelease == false`, and an exact stable `skill-vMAJOR.MINOR.PATCH` tag using valid nonnegative numeric version components. Reject prerelease suffixes and unknown tag formats for review rather than treating them as stable.
2. Compare the parsed numeric version tuple, not lexicographic names, API order, tag dates, or publication dates. Select its maximum. A newer publication of an older maintenance version must not downgrade the selected stable version.
3. Record the release ID, tag name, tag-object identity and peeled commit, selected asset IDs/names/sizes/digests, and packaging-procedure revision. Compare against the last qualified publication's provenance. Pin consumed content to these identities; never use a moving branch as the upstream input.
4. Incomplete enumeration, unavailable required assets, inconsistent identity, or a selected version below the last qualified version must stop promotion. A no-change result means the selected identities still match; checking only the tag string is insufficient.

This is a proposed contract. The inspected stable maximum was **`skill-v4.8.0`**, release **424884908**, published **2026-10-26T23:41:42Z**. Its annotated tag object was `09aef2fd2e3a2c7138f3e1a6cbbbdcb3f4087c2d`, pointing to commit `414603bf14c7a344edb466bb1f85690c77ce8b7d`. The release reported `immutable: false`. Its `universal.zip` asset ID was **679840857**, with API-reported SHA-256 `82e6f6ff3a2b18f46f0f2fc388c1ab7abf3ccc52bbfc522456396d13011d6706`. I inspected metadata, not the archive bytes. [Release record](https://api.github.com/repos/pbakaus/impeccable/releases/424884908), [tag ref](https://api.github.com/repos/pbakaus/impeccable/git/ref/tags/skill-v4.8.0), [annotated tag](https://api.github.com/repos/pbakaus/impeccable/git/tags/09aef2fd2e3a2c7138f3e1a6cbbbdcb3f4087c2d)

Treat a changed tag target, replaced/missing selected asset, or changed digest for an already pinned version as an input-integrity incident. Re-read those inputs before promotion and hash the downloaded bytes against the recorded digest. Stop and preserve the last qualified publication on disagreement; do not silently overwrite an existing version or reuse its old qualification. Git refs can be rewritten and release assets can be edited or deleted, so a release name is not an immutable identity. Metadata-only release-note edits need not invalidate package bytes; provenance should distinguish consumed inputs from descriptive metadata. [Git references](https://docs.github.com/en/rest/git/refs), [Release assets API](https://docs.github.com/en/rest/releases/assets)

After missed runs, enumerate current releases again and select the highest stable version. This catches up to the current target without relying on a missed event. It does not promise to publish every intervening version, or discover a release removed between checks. The current destination calls for up-to-date releases, not a complete historical mirror.

### API budget and failure handling

Authenticate public API reads with the workflow token where supported. GitHub documents **1,000 requests/hour/repository** for `GITHUB_TOKEN`; unauthenticated requests have a **60/hour/IP** limit. Current enumeration needs one list page plus a small number of identity/provenance reads, rather than a request per historical release. No live workflow-token request count was measured. Public release and ref endpoints permit public-resource reads without the corresponding repository permission; the actual fork-token route remains a qualification observation. [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Release API](https://docs.github.com/en/rest/releases/releases), [Git reference API](https://docs.github.com/en/rest/git/refs)

Make requests serially and respect `Retry-After` and rate-reset headers. Use bounded backoff for secondary limits and fail the check without promotion when exhausted. Authenticated conditional requests returning `304` avoid primary-limit consumption, but retaining validators is an optional optimization; do not add an Actions cache or hourly state commits solely for it. Complete enumeration and direct tag/asset checks remain necessary: a cached release-list response alone cannot prove a tag target unchanged. [GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## Freshness, observation, and recovery

The supported statement is: **“Attempt a check every hour; after a successful complete check and successful qualification, publish the selected stable version through the reviewed procedure.”** It is not a maximum-age guarantee. GitHub can delay schedules or drop queued jobs under load; an offset minute reduces the documented top-of-hour risk but supplies no deadline. Scheduled workflows execute the latest default-branch commit, and the workflow must exist there. [Schedule behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

| Condition | Observation and recovery route |
| --- | --- |
| Delayed or missing scheduled run | Inspect workflow run history and the timestamp of the last completed successful check. Trigger the same workflow manually after checking service/workflow state. A successful manual run establishes recovery once; it does not prove later schedules resumed. |
| Public fork or inactivity disablement | Inspect both repository Actions enablement and the individual workflow's state. Public-fork schedules begin disabled, and 60 days without repository activity disables public schedules. Re-enable the intended workflow, dispatch it, and later observe an actual scheduled completion. Do not assume repeated no-op checks prevent inactivity disablement. |
| Schedule actor unavailable | A suspended, deleted, or deprovisioned associated actor can stop schedules even while manual runs work. A writer can change the cron in a reviewed commit to establish an active actor, then verify scheduled execution. |
| API/network error or invalid candidate | Keep the last qualified ref and release. A later scheduled or manual run starts from durable provenance and current upstream state. Failed or partial checks must not be reported as successful freshness checks. |
| Publication interrupted | Reconcile the existing candidate release and uploaded hashes before resuming. Advance the marketplace ref only after all required checks and final asset verification succeed. Avoid duplicate releases and never replace differing bytes under an already qualified version. This recovery behavior needs an implementation test. |

The enable/disable controls exist in the UI, REST API, and CLI. Manual execution requires write access and `workflow_dispatch` on the default branch; the CLI can select a ref. Recovery should explicitly use the reviewed default-branch procedure rather than an arbitrary historical ref. [Workflow enablement](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows), [manual runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), [schedule actor troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#scheduled-workflow-stopped-running)

Record check start/completion, selected upstream identities, no-change/published/failed outcome, packaging revision, and the last qualified publication in the run summary and release provenance. Missing runs cannot notify from inside a workflow that never starts; an unattended finite staleness bound would require a separately selected watchdog and response policy. Neither is needed to support the requested hourly *attempt cadence*. Without successful execution and recovery, staleness is unbounded.

Publication and consumption need separate clocks. OpenAI's workspace GitHub marketplace documentation describes daily checks and a manual **Sync now** control; a branch follows updates while a fixed commit stays pinned. Consequently hourly archive/ref publication does not establish hourly workspace adoption. Local-client update and Codex Cloud plugin behavior still require their own qualification observations. [OpenAI marketplace synchronization](https://learn.chatgpt.com/docs/enterprise/plugin-management)

## Publisher and main protection

At inspection, `nisavid/impeccable` was public with default branch `main`; repository Actions were disabled. The active `main-preservation` ruleset matched only `refs/heads/main`, blocked deletion and non-fast-forward updates, and had no bypass actors. It did **not** contain a pull-request requirement. Workflow-token defaults were read-only, with approving PR reviews disabled. These are current observations, not recommendations to retain temporary disablement or omit the selected PR policy. [Repository](https://api.github.com/repos/nisavid/impeccable), [Actions permission](https://api.github.com/repos/nisavid/impeccable/actions/permissions), [ruleset](https://github.com/nisavid/impeccable/rules/26671100), [token defaults](https://api.github.com/repos/nisavid/impeccable/actions/permissions/workflow)

Use the built-in repository-scoped `GITHUB_TOKEN` as the initial publisher candidate, with explicit minimum job permissions. Ordinary release creation requires `contents: write`; the same permission supports ordinary ref updates, subject to applicable rules. A default read setting is not evidence that a publishing job already has write permission. Do not grant review approval, administration, or a ruleset bypass for this route. Token-backed push/release events do not automatically start follow-up workflows; finish required verification in the publishing workflow. GitHub separately documents approval-required runs for some token-created PR events, so a future PR-based publisher cannot assume unattended CI. [Token permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token), [Release creation](https://docs.github.com/en/rest/releases/releases#create-a-release), [ref updates](https://docs.github.com/en/rest/git/refs#update-a-reference), [token behavior](https://docs.github.com/en/actions/concepts/security/github_token)

The inherited `.github/workflows/sync-generated-output.yml` requests `contents: write`, optionally substitutes `SYNC_GENERATED_OUTPUT_TOKEN`, rebuilds generated output, and pushes `HEAD:main` directly with retries. Its source was inspected at remote main commit `c3bb418ee38ee49a6b999b7752c1368f3123a2bd`. Once a required-PR/approval rule with no bypass is applied, that direct update cannot simply remain the publisher: it must satisfy the PR policy or be disabled/replaced for the fork. A write token is not a bypass. [Inspected workflow](https://github.com/nisavid/impeccable/blob/c3bb418ee38ee49a6b999b7752c1368f3123a2bd/.github/workflows/sync-generated-output.yml), [required-PR rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)

A dedicated distribution branch or other qualified moving ref can separate routine artifact promotion from protected source changes on `main`. This is the smallest candidate worth considering before adding a new actor, bypass, or service, but its exact name, permissions, update shape, and consumer compatibility remain part of the packaging/publication decision. Do not silently choose `main` as the marketplace ref or use an unprotected ref to change protected source policy. Reconcile the inherited workflow and all intended triggers before later Actions enablement; this research does not authorize enabling them.

## Decisions now supported and remaining evidence

- **Supported:** hourly checks meet the stated zero-incremental-charge condition under the specified runner/storage/service exclusions. No new cadence approval is needed on cost grounds.
- **Supported:** select the stable skill stream by parsed version after complete enumeration; preserve immutable input provenance separately from a moving consumer ref.
- **Supported:** best-effort hourly attempts, catch-up to the currently highest eligible version, manual recovery, and retention of the last qualified publication. There is no documented one-hour publication or consumer-freshness guarantee.
- **Still to settle in the publication decision:** the qualified package/procedure, moving-ref projection, publisher authorization under the final rules, and a named maintainer's stale-run response expectations. A stricter freshness bound would be a new requirement, not a property of cron.
- **Still to observe in a separately authorized execution workflow:** a no-change check, correct component selection, a real scheduled completion and manual recovery, fork-token upstream reads and intended writes, rejection of changed pinned inputs, interrupted-publication recovery, preservation on failed checks, and actual consumer update behavior. Fixtures can establish selector logic, but cannot prove GitHub scheduling, permission enforcement, billing, or client adoption.
